# Territory Riders — продуктова концепція

## 1. Суть продукту

**Territory Riders** — соціальна геогра для велосипедистів. Користувач не просто записує поїздку, а створює на реальній карті власну територію. Щоб отримати зону, він стартує, прокладає маршрут і повертається до стартової області, замикаючи контур. Завершений контур стає заявкою на територію; сервер перевіряє GPS-трек, обчислює геометрію та публікує результат для спільноти.

Ключова емоція: **«мій район змінюється, бо я проїхав його»**. Учасники бачать кольорові межі один одного, але не отримують точного live-маршруту суперника без його згоди.

## 2. Правила MVP

| Правило | Пропонована реалізація |
|---|---|
| Старт | Користувач натискає «Почати поїздку» і дозволяє foreground location; Android може перейти у foreground service для фонового трекінгу. |
| Замикання | Трек вважається замкненим, якщо остання точка не далі 80 м від першої, у маршруті є щонайменше 4 точки, а довжина поїздки не менша 1 км. Значення мають бути конфігурованими для сезону. |
| Нова територія | Замкнений маршрут перетворюється на полігон. Площа розраховується сервером у метричній проєкції, а не на клієнті як джерелі істини. |
| Захоплення всередині | Чужі зони, усі контрольні точки яких опинилися всередині нового полігона, переходять до нового власника. |
| Відсікання | Якщо новий контур перетинає чужу територію, виконується polygon difference: відрізана частина стає новою зоною нападника, залишок залишається власнику. |
| Об’єднання | Суміжні полігони одного користувача об’єднуються, але історія змін зберігається окремо. |
| Конфлікт | Якщо два треки завершилися майже одночасно, сервер приймає їх у порядку валідованого часу отримання та показує подію в історії. |
| Відкат | Підозрілу або помилково валідовану подію можна позначити для модерації; автоматичне знищення чужої історії не застосовується. |

### Що не зараховується

Не зараховуються маршрути з GPS-стрибками, нереалістичною швидкістю для велосипеда, надмірними пропусками даних, самоперетином без валідної геометрії, замалим контуром, повторною відправкою того самого треку або точками, які очевидно створені емулятором. Перший реліз не повинен карати користувача без пояснення: статус має бути **«потребує перевірки»** з можливістю подати трек повторно.

## 3. Соціальний шар

Кожна територія має власника, стабільний колір, площу, дату останньої зміни та історію подій. На карті є режими **«Усі»**, **«Моя»** і **«Поруч»**. Натискання на полігон відкриває bottom sheet із власником, площею, останньою зміною і переходом у профіль.

Події поділяються на три види: **захоплення** (користувач зайняв чужу або вільну зону), **відсікання** (змінилася частина території іншого гравця) та **досягнення** (рекорд, серія, нова позиція). Власник зміненої території отримує push-повідомлення на Android і бачить подію в стрічці після синхронізації.

Рейтинг у MVP рахується за площею, захопленою в поточному сезоні, із додатковими показниками за успішні замкнені кола та захист території. Загальний рейтинг не повинен винагороджувати лише кількість поїздок, інакше перевагу отримають користувачі з більшим вільним часом.

## 4. Приватність і безпека

За замовчуванням соціальна карта показує лише завершені полігони. Live-позиція прихована. Користувач може дозволити live-режим окремо, але додаток пояснює наслідки перед увімкненням. У повідомленні про атаку показуються факт і площа зміни, а не точний маршрут суперника.

GPS-трек потрібен для валідації, але для довготривалого відображення можна зберігати спрощену геометрію, а сирі точки видаляти після періоду, визначеного політикою зберігання. Для профілю потрібні налаштування видимості, видалення акаунта й експорту даних.

## 5. Карта та OpenStreetMap

Для обох клієнтів використовується OpenStreetMap як джерело базової карти. На карті має постійно бути видима атрибуція **© OpenStreetMap contributors** із переходом на сторінку ліцензії. Для стандартних тайлів політика OSM вказує URL `https://tile.openstreetmap.org/{z}/{x}/{y}.png`; необхідно поважати кешування та не створювати надмірне навантаження на публічну інфраструктуру [1]. Дані OSM поширюються за ODbL із вимогою кредитувати OpenStreetMap та його учасників [2].

У демо-клієнті web карта використовує OSM tile із візуальним шаром територій, а native-клієнт — `react-native-maps` з OSM `UrlTile`. Перед масштабним запуском потрібно перейти на керований tile-провайдер або власну tile-інфраструктуру, не змінюючи атрибуцію.

## 6. Архітектура

Мобільний і веб-клієнт використовують спільні TypeScript-типа території, подій та геометричних правил. Android відповідає за GPS-запис, foreground service, локальне кешування і push-інтерфейс. Веб відповідає за дослідження карти, соціальну стрічку, рейтинг і профіль.

Сервер є джерелом істини для геометрії. Основні сутності: `users`, `rides`, `territories`, `activityEvents`, а для production також `pushTokens`, `seasonSnapshots` і `moderationCases`. Завершений трек надсилається як заявка, сервер валідовує його, створює/оновлює території, створює адресні події для власників і відправляє push-повідомлення.

| Шар | MVP | Production hardening |
|---|---|---|
| Клієнт | Expo Android + Expo web, локальні demo-дані, OSM tiles, маршрут і події | Offline queue, conflict resolution, tile caching, analytics без збору зайвих точок |
| API | tRPC `territory.list`, `territory.activity`, `territory.submitRide` | Авторизація, idempotency key, pagination, rate limits, WebSocket/SSE або коротке оновлення |
| Геометрія | Детерміновані TypeScript helpers і серверна валідація | GEOS/PostGIS-подібна robust polygon difference, топологічні перевірки, модерація |
| Сповіщення | Локальне повідомлення після демо-результату | Expo push token, адресна доставка власнику, налаштування категорій і retry |
| Карта | OpenStreetMap base map з атрибуцією | Керований tile-провайдер/власний кеш під зростаюче навантаження |

## 7. Монетизація без руйнування гри

У першому сезоні гра має бути безкоштовною. Потенційні майбутні джерела доходу — брендовані міські челенджі, партнерські точки відпочинку, косметичні профільні теми та командні турніри. Не варто продавати перевагу на карті або можливість захоплювати територію без поїздки: це зруйнує довіру до механіки.

## 8. Що вже реалізовано в прототипі

У поточному проєкті є фірмовий темний карта-first інтерфейс, вкладки карти/поїздки/подій/профілю, екран результату, правила, налаштування приватності, демонстраційні полігони Києва, OSM attribution, локальний трекінг, Android background location plumbing, локальне сповіщення, серверні таблиці територій/поїздок/подій, tRPC endpoints і тести геометрії.

## 9. Наступна ітерація

Першим production-кроком має бути підключення Manus OAuth на Android/web і реєстрація push token для конкретного користувача. Далі слід замінити demo-дані на `territory.list`/`territory.activity`, додати server-side polygon clipping, реалізувати idempotent ride submission та провести польове тестування GPS на фізичних Android-пристроях.
